Inference-serving reliability · measured

Localizing p99 TTFT inside a vLLM server

Every LLM-serving team alerts on time-to-first-token. Almost nobody can say what made it spike. I pointed a change-point pipeline at the inside of the server, built a labelled fault corpus on a real GPU, and measured how often it got the answer right.

39%top-1 accuracy

§ 1

The suspects all look the same

p99 TTFT spikes. You open the Grafana board. Now what?

There are four usual suspects: KV cache pressure, batch scheduling stalls, prefix-cache collapse, and preemption. The telemetry to tell them apart is not missing. It is all there, at one-second resolution. The problem is that all four look nearly identical from the outside, and each one can cause the others.

Preemption is a good example. It slows requests down, so it is a cause of latency. It also happens because the cache filled up, so it is an effect of cache pressure. Rank your metrics by how well they correlate with TTFT and both light up. The correlation is real in both directions, which is exactly why it cannot tell you which came first.

Thresholds have the same problem from the other side. Alert on kv_cache_usage_perc and it fires during a plain traffic ramp, during a prefix-cache collapse, and during a genuine misconfiguration. You learn that something is wrong. You already knew that.

So the target here is not detection. Detection is easy. The target is attribution.

§ 2

An inference server is one service, so localize inside it

I started from an FChain-style pipeline built for microservice RCA. It finds change points in each service's metrics, estimates when each deviation really began, and ranks services by which moved first, filtered through the call graph.

Pointing that at vLLM does not work on its own. An inference server is a single process. There are no services to rank, and the dependency layers have no graph to walk.

The fix is to change what gets localized. Instead of services, rank mechanisms. The vLLM scheduler has real internal causal structure: cache occupancy drives preemption, preemption drives queueing, queueing drives TTFT. That structure is a DAG, and everything the pipeline already does to a service graph works on it unchanged.

Two useful things fall out of the domain that a generic pipeline would never know about.

TTFT splits in two, for free

vLLM already exports request_queue_time_seconds and request_prefill_time_seconds as separate histograms. TTFT is roughly their sum. That single split cuts the hypothesis space in half before any analysis runs. If the time went to queueing, the cause is on the admission side. If it went to prefill, the cause is on the compute side. Most dashboards throw this away by plotting only the total.

Load causes everything, so load cannot be the answer

Rank purely by which signal moved first and arrival_load wins every single incident. Traffic moves first in real systems. That is not a finding, it is a tautology.

Marking those nodes as exogenous fixes it. They are inputs you do not control, not defects. It also buys a second kind of answer. If the first thing to move is exogenous and load is climbing, the verdict is capacity: you are being asked for more than you can serve, and nothing is broken. If load is flat and something internal moves first, it is a pathology. That is the difference between adding a replica and fixing your config, and a threshold alert cannot make it.

§ 3

What I actually measured

I did not want to claim that this works. I wanted to claim that it works this often, against these alternatives. That needs a labelled corpus, and building one is the step most RCA write-ups skip.

One L4 GPU, one session. 38 scorable runs across seven fault scenarios, covering five distinct mechanisms. Eight of the runs are clean, with nothing wrong at all, so the false-positive rate is measured rather than assumed.

Most of the faults are workload shaping rather than infrastructure chaos. A prefix-diversity attack gives every request a unique prefix. A long-output burst makes sequences hold their blocks for minutes. A bimodal mix pairs very short requests with very long ones. These are cheap to run and far more repeatable than killing containers. The rest are config faults, where the server restarts in a degraded state, and each restart is its own labelled fault.

Every run writes a metrics.parquet and a ground_truth.json, and both are committed. Scoring replays those files from disk. No GPU, no cluster, no running server.

§ 4

The result, including the part that stings

A top-1 number on its own tells you nothing about whether eight layers of statistics were worth writing. So the pipeline is scored against three simple baselines and against a frontier model given the same evidence.

The uncomfortable row

Static threshold alerting wins top-1. Three points ahead of the thing I built. If top-1 were the only number I reported, the honest conclusion would be that the pipeline is not worth running.

The rest of the row is why it is still worth running. Threshold alerting is useless past its first guess. Its top-3 is identical to its top-1, because once the first runbook rule fires there is nothing meaningful behind it. The pipeline gives you a ranked shortlist you can work down. Against threshold that is 32 more points of top-3 and 0.14 more MRR.

Compare instead against whichever baseline is strongest on each metric and the win gets much smaller: 7.9 points of top-3 over the language model, and 0.06 MRR over correlation. That is the number I would defend. The pipeline leads on ranked quality, and it leads consistently, but the margin is modest and I am not going to dress it up.

Correlation does exactly what I predicted it would. It ties on top-1 and loses 13 points of top-3, because it cannot separate a cause from its own effect. Topology is the floor: it ignores the telemetry completely and just blames whatever sits furthest upstream. It still scores 58% top-3, which is a good reminder of how much a shortlist gets for free from knowing the architecture. It also names something on every single clean run.

Claude Opus 5 gets 34% top-1 and 0.496 MRR from the same per-component evidence. That is competitive, and better than I expected. It is also the fairest answer I have to “why not just ask a model?” The gap is that the model never sees onset timing, and onset timing is the whole basis of the pipeline's ranking. Which suggests the interesting system is neither one alone, but a model reading the pipeline's timing output.

§ 5

The dominant failure is not statistical

The confusion matrix is where the real finding is.

The finding

The pipeline ranks by which mechanism moved first. But it reads “first” from the telemetry, not from the event. How a metric is measured decides when it appears to move. So an effect read from a gauge beats its own cause read from a rate, every time.

Gauges report immediately. kv_cache_usage_perc and num_requests_running show their new value on the very next scrape. Windowed rates and histogram quantiles do not. rate(...[30s]) and histogram_quantile over buckets only reach their new value once the window has filled, which is roughly half a window late.

Two mechanisms in this domain are read from instantaneous gauges. Those are precisely the two columns collecting the misses. The pipeline compensates by shifting each series back by half its window before ranking, which is worth 2.7 points of top-1 on this corpus, so it stays on. But it is a patch, not a fix. Fixing it properly means changing what gets measured, not how it gets ranked.

This is the most useful thing the project turned up, because it is not about vLLM. Any method that ranks causes by onset order over Prometheus data has this problem, and I have not seen it written down. It also means a published accuracy number for this class of method is partly measuring the exporter's design choices.

§ 6

Two things wrong with my own corpus

I found both of these while building the results page, which is an argument for building the results page.

Nine runs never had a clean baseline

Each run does the same thing: record a baseline, inject a fault, record the fault window, repeat. Sometimes the previous run's load had not finished draining. When that happens the baseline window opens with p99 TTFT already 300 to 600 times its own median.

That breaks the detector. Layer 1 works out a mean and a standard deviation from the baseline window, and a huge standard deviation means nothing in the fault window ever looks unusual enough to flag. The validity check I had written passes these runs, because it only looks at whether the load generator was keeping up. It was. The server was just still busy with the last incident.

Top-1 on those nine runs is 11%. On the twenty-nine that started quiet it is 48%. The headline 39% counts all thirty-eight anyway. Dropping a quarter of your corpus raises your score, and that is a move you make in the open or not at all, so it is reported here and left out of the totals.

The SLI is coarsely bucketed

time_to_first_token_seconds is a Prometheus histogram, and p99 is interpolated from its buckets. Across these traces the quantile spends most of its time stuck on two values, 0.248 s and 159.2 s. Those are bucket edges, not measurements. Real but small TTFT movements are invisible, and the SLI reads as a staircase instead of a curve. Getting finer detail means setting custom bucket boundaries at deploy time.

§ 7

What I would do differently

  • Instrument onset directly. The measurement bias cannot be fixed downstream. A small exporter that emits a timestamp whenever a mechanism crosses a state boundary would remove the biggest source of error outright. The cost is that it stops being black-box.
  • Check the SLI before opening a baseline window, not just the load. One extra condition would have saved nine runs and about a third of the GPU budget.
  • Set histogram buckets before capturing. Bucket boundaries are a deploy-time decision. I worked out that they mattered after the GPU was already returned.
  • Fewer scenarios, more repeats. Three runs of queue_starved cannot tell a real weakness apart from noise. Five mechanisms measured properly would say more than seven measured thinly.

§ 8

Reproducing it

The traces are in the repository. Scoring replays them from Parquet, so a fresh clone re-derives every number on this page without a GPU.

The pipeline is deterministic. Layer 1's block bootstrap is seeded per component and metric, which I added after noticing that running the same evaluation twice gave different top-3 numbers. The threshold is a percentile of a thousand random resamples, so change points sitting near it were flipping between runs. 

git clone https://github.com/aryansharma2k2/microservice-blackbox-rca
cd microservice-blackbox-rca
pip install -e ".[dev]"

make eval

CI checks the accuracy on every push, against both a floor and a false-positive ceiling taken from the measurements above. A change that quietly makes the diagnosis worse fails the build.
