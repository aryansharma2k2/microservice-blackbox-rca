Localizing p99 TTFT inside a vLLM server

Time-to-first-token is the SLI every LLM-serving team alerts on and nobody can attribute. This is what happened when I pointed a change-point pipeline at the inside of the server, built a labelled fault corpus on a real GPU, and measured how often it was right.

§ 1

The suspects all look the same

When p99 TTFT spikes, the on-call engineer opens a Grafana board and guesses. The candidates are KV cache pressure, batch scheduling stalls, prefix-cache collapse, and preemption — and the reason the guess is hard is not that the telemetry is missing. It is all there, at one-second resolution. The problem is that these mechanisms are observationally confusable: they share symptoms, and they cause one another.

Preemption is simultaneously a cause of latency and an effect of cache pressure. So ranking metrics by correlation with the SLI implicates both and separates neither — the correlation is real in both directions. A static threshold on kv_cache_usage_perc fires during a plain load ramp, during a prefix-cache collapse, and during a genuine misconfiguration, with no way to tell you which one you are in.

That is the gap this project aims at: not detecting that something is wrong, which is easy, but attributing it, which is not.

§ 2

An inference server is one service, so localize inside it

I started from an FChain-style pipeline built for microservice RCA: eight layers that find change points in per-service metrics, estimate when each deviation actually began, and rank services by onset order filtered through a call graph.

Pointing that at vLLM naively does not work. An inference server is a single process, so there is nothing to localize across, and the dependency layers have no graph to operate on. The retarget only becomes interesting with a reframe: the localization domain changes from services to mechanisms. The vLLM scheduler has genuine internal causal structure — cache occupancy drives preemption, preemption drives queueing, queueing drives TTFT — and that structure is a DAG. Onset ordering and graph filtering apply to it unchanged.

Two things fall out of the domain that a generic pipeline could not have known.

TTFT decomposes natively

vLLM exposes request_queue_time_seconds and request_prefill_time_seconds as separate histograms. TTFT is approximately their sum, so the split partitions the hypothesis space before any inference runs: queue-dominated points at admission-side causes, prefill-dominated at compute-side. That is free information the metric endpoint hands you, and most dashboards throw it away by plotting only the total.

Load causes everything, so load cannot be the answer

Rank by earliest onset and arrival_load wins every incident, because in a real system traffic moves first. Marking nodes as exogenous — uncontrolled inputs rather than faults — fixes this, and produces a second kind of answer worth having. If the earliest onset is exogenous and load is climbing, the verdict is capacity: you are simply overloaded and nothing is broken. If load is flat and an internal node fires first, it is a pathology. That is the difference between “add a replica” and “fix your config,” and it is the distinction an alert threshold structurally cannot make.

§ 3

What I actually measured

The claim I wanted to be able to defend was not “this works” but “this works this often, against these alternatives.” That requires a labelled corpus, which is the part most RCA projects skip.

One L4 GPU, one session: 38 scorable runs across seven fault scenarios covering five distinct mechanisms, plus eight clean runs so the false-positive rate is measurable rather than assumed. Most faults are workload shaping rather than infrastructure chaos — a prefix-diversity attack that gives every request a unique prefix, a long-output burst that makes sequences hold their blocks for minutes, a bimodal short/long mix. These are cheaper and far more reproducible than killing containers. Config-side faults restart the server degraded, and each restart is a labelled fault.

Every run writes metrics.parquet and ground_truth.json, both committed. Scoring replays from disk, so every number here is re-derivable with no GPU, no cluster, and no server.

§ 4

The result, including the part that stings

A top-1 number in isolation says nothing about whether eight layers of statistics earn their complexity. So the pipeline is scored against three classical baselines and against a frontier model given the same evidence.

The uncomfortable row

Static threshold alerting wins top-1. Three points ahead of the thing I built. If I only reported top-1, the honest conclusion would be that the pipeline is not worth running.

It is worth running for a different reason, and the rest of the row says why: threshold alerting is useless past rank 1. Its top-3 never improves on its top-1, because once the first runbook rule fires there is nothing meaningful behind it. Against it the pipeline is +32 points of top-3 and +0.14 MRR. What the pipeline produces is a ranked shortlist an engineer can work down; what a threshold produces is one guess and a shrug.

The fairer comparison is against whichever baseline is strongest on each metric, and it is a narrower win: +7.9 points of top-3 over the language model and +0.06 MRR over correlation. That is the number I would defend. The pipeline leads on ranked quality, it leads consistently, and the lead is real but not large.

Correlation behaves exactly as predicted: it ties on top-1 and loses 13 points of top-3, because it cannot separate a cause from its own effect. Topology — always blame the graph root, ignoring telemetry entirely — scores a non-trivial 58% top-3, which is a useful reminder of how much a shortlist gets for free from knowing the architecture, and it names something on every clean run.

Claude Opus 5, handed the same per-component before/after evidence, reaches 34% top-1 and 0.496 MRR — genuinely competitive, and better than I expected. It is also the fairest available answer to “why not just ask a model?” The gap is that the model never sees onset timing, and onset ordering is the pipeline's entire mechanism. That suggests the interesting system is not one or the other but the model reading the pipeline's timing output, which is roughly what the explainer stage does.

§ 5

The dominant failure is not statistical

The confusion matrix is where the actual finding lives.

The finding

The pipeline ranks by onset order, and onset is measured from the telemetry — not from the event. How a metric is measured determines when it appears to move. A gauge-backed effect systematically outranks its own rate-backed cause.

Gauges — kv_cache_usage_perc, num_requests_running — report their new value on the very next scrape. Windowed rates and histogram quantiles — rate(...[30s]), histogram_quantile over buckets — only reach their new value once the window fills, roughly half a window late. Two mechanisms in this domain are read from instantaneous gauges, and those are precisely the two columns absorbing the off-diagonal mass.

The pipeline compensates by shifting each series back by half its window before ranking. A/B'd on this corpus that is worth +2.7 points of top-1, so it stays on — but it is a correction, not a cure. Fixing this properly means changing what is measured, not how it is ranked: exporting per-mechanism event timestamps rather than inferring onset from aggregates.

I find this the most useful thing the project produced, because it generalizes past vLLM. Any onset-ordering method run over a Prometheus scrape is subject to it, and I have not seen it stated. It also means a published top-1 number for this class of method is partly a measurement of the exporter's design.

§ 6

Two things wrong with my own corpus

Both of these I found while building the results page, which is an argument for building the results page.

Nine runs never had a clean baseline

The capture protocol runs baseline, inject, fault, repeat. When the previous run's load has not finished draining, the baseline window opens with p99 TTFT already 300–600× its own median. Layer 1 calibrates its mean and standard deviation from that window, so an inflated sigma desensitizes the detector and nothing in the fault window clears threshold. The validity check I had written passes these runs — it looks at offered-versus-completed throughput and backlog growth, and by those measures the load generator was healthy. The server was simply still working off the last incident.

Top-1 is 11% on those nine runs and 48% on the twenty-nine that started quiet. The headline 39% counts all thirty-eight anyway. Dropping a quarter of a corpus raises your score, and that is a move that should be argued in the open rather than applied quietly — so it is reported and left out of the totals.

The SLI is coarsely bucketed

time_to_first_token_seconds is a Prometheus histogram, and p99 is interpolated from its buckets. Across these traces the quantile spends most of its time pinned to two values — 0.248 s and 159.2 s — which are bucket edges, not measurements. Genuine small TTFT movements are invisible, and the SLI reads as a step function rather than a curve. Anything finer needs custom bucket boundaries set at deploy time.

§ 7

What I would do differently

  • Instrument onset directly. The measurement-modality bias is not fixable downstream. A small exporter emitting a timestamp when each mechanism crosses a state boundary would remove the dominant error source entirely, at the cost of no longer being black-box.
  • Gate the baseline on the SLI, not just on load. One additional check — the SLI must be within a few multiples of its own median before the window opens — would have saved nine runs and roughly a third of the GPU budget.
  • Set histogram buckets before capturing. Bucket boundaries are a deploy-time decision, and I discovered they mattered after the GPU was returned.
  • More repeats per scenario, fewer scenarios. Three runs of queue_starved cannot distinguish a real weakness from noise. Five mechanisms measured well would say more than seven measured thinly.

§ 8

Reproducing it

The traces are in the repository. Scoring replays them from Parquet, so a clean clone re-derives every number on this page without a GPU. The pipeline is deterministic — Layer 1's block bootstrap is seeded per (component, metric), after I found that repeated evaluations of the same corpus were producing different top-3 numbers. 

git clone https://github.com/aryansharma2k2/microservice-blackbox-rca
cd microservice-blackbox-rca
pip install -e ".[dev]"

make eval

CI asserts diagnostic accuracy on every push — an accuracy floor and a false-positive ceiling, both derived from measurement rather than aspiration — so a change that quietly degrades diagnosis fails the build.
