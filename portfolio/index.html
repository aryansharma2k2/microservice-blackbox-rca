When p99 TTFT spikes, which subsystem did it?

Time-to-first-token is the SLI every LLM-serving team alerts on and nobody can attribute. The suspects — KV cache pressure, batch scheduling, prefix-cache collapse, preemption — share symptoms and cause one another. Preemption is simultaneously a cause of latency and an effect of cache pressure, so correlation implicates both and separates neither.

This is an eight-layer change-point pipeline pointed at the inside of one process, localizing among mechanisms rather than across services. Scored on — labelled runs captured on a real L4 GPU, against three classical baselines and Claude Opus 5 given identical evidence.

Measured, not asserted

Does eight layers of statistics beat the obvious thing?

A top-1 number alone says nothing about whether the complexity is earned. Every method below sees the same evidence from the same — runs and is scored identically. Threshold alerting wins top-1. It is also useless past rank 1 — which is the honest shape of this result.

How to read this

Threshold alerting fires runbook rules in order, so its first guess is decent and its second is noise — top-3 never improves on top-1. Correlation ties the pipeline on top-1 and loses 13 points of top-3, exactly as predicted: it cannot separate a cause from its own effect. Topology ignores telemetry entirely and names something on every clean run — the floor any real method has to clear. Claude Opus 5, given the same per-component before/after evidence, is genuinely competitive — but it never sees onset timing, and onset ordering is the pipeline's whole edge.

The reframe

An inference server is one service — so localize inside it

A naive port of microservice RCA leaves the dependency layers with nothing to operate on. The vLLM scheduler has real internal causal structure that forms a DAG, so the localization domain changes from services to mechanisms. The statistical core needs zero modification; only the metric registry and this graph are domain-specific.

Exogenous — uncontrolled input. Load causes everything, so a naive onset ranking blames it for every incident. These nodes can drive a capacity verdict but are never named as a pathology.

SLI — the sink being explained. Excluded from its own root-cause list, so the engine cannot answer “TTFT is slow because TTFT is slow.”

Mechanism — a subsystem state backed by one or more Prometheus series. Hover any node for its metrics.

The part most projects omit

Where it fails, and why

Rows are the injected mechanism; columns are what the pipeline named. A perfect diagnoser is diagonal. This one is not, and the off-diagonal mass has a single dominant explanation.

Measurement modality outranks causality

The pipeline ranks by onset order, and onset is measured from the telemetry — not from the event. Gauges like kv_cache_usage_perc and num_requests_running report their new value on the very next scrape. Windowed rates and histogram quantiles — rate(...[30s]), histogram_quantile over buckets — only reach their new value after the window fills, roughly half a window late.

So a gauge-backed effect systematically appears to precede its own rate-backed cause. That is why kv_cache_pressure and batch_composition absorb most of the off-diagonal mass: they are the two mechanisms read from instantaneous gauges. The pipeline compensates by shifting each series back by half its window, worth +2.7 points of top-1 when A/B'd on this corpus — but it is a correction, not a cure. Fixing this properly means changing what is measured, not how it is ranked.

A quarter of the corpus never had a clean baseline

—

The capture protocol runs baseline, inject, fault, repeat. When the previous run's load has not finished draining, the baseline window opens with p99 TTFT already two orders of magnitude above its own median. Layer 1 calibrates its mean and standard deviation from that window, so an inflated sigma desensitizes the detector and nothing in the fault window clears threshold. The existing validity check passes these runs — it looks at offered-versus-completed throughput and backlog growth, and by those measures the load generator was healthy; the server was simply still working off the last incident.

The headline number above counts all — runs anyway. Dropping a quarter of a corpus raises the score, and a change like that should be argued in the open rather than applied quietly — so it is reported here and left out of the totals.

The SLI is coarsely bucketed

vllm:time_to_first_token_seconds is a Prometheus histogram, and p99 is interpolated from its buckets. Across these traces the quantile spends most of its time pinned to two values — 0.248 s and 159.2 s — which are bucket edges, not measurements. Small genuine TTFT movements are therefore invisible, and the SLI reads as a step function rather than a curve. Anything finer needs either custom bucket boundaries at deploy time or per-request timings the metrics endpoint does not expose.

Method

Eight layers, and what each one is for

  1. 1

    CUSUM + block bootstrap

    Find candidate change points per metric. The detection threshold is calibrated empirically — the 95th percentile of 1000 block-bootstrap resamples of the baseline — rather than assumed. Seeded per (component, metric), so the whole pipeline is reproducible.

  2. 2

    Markov normal model

    Drop changes that a model of learned-normal behaviour still predicts. Detectable is not the same as abnormal.

  3. 3

    FFT burst filter

    Remove periodic workload bursts that are expected at this frequency, so a predictable traffic shape does not register as an incident.

  4. 4

    Tangent rollback

    A detector fires after the trend starts. Roll each crossing back along its tangent to estimate when the deviation actually began — the number every later layer depends on.

  5. 5

    Multi-metric aggregation

    Collapse per-metric onsets into one onset per mechanism, and apply lag compensation for windowed metrics.

  6. 6

    Exogenous check & verdict

    If the earliest onset is an exogenous node and load is climbing, the answer is capacity — you are overloaded, nothing is broken. If load is flat and an internal node fires first, it is a pathology. Distinguishing these is the difference between “add a replica” and “fix your config.”

  7. 7

    Propagation chain

    Order candidates by onset, treating near-simultaneous fires as concurrent rather than sequential.

  8. 8

    Dependency filter

    Demote any mechanism the graph explains as propagation from something earlier. This is what stops the engine from reporting a symptom chain as five separate root causes.

The effect-size gate

Layers 1–4 test whether a change is detectable, never whether it is large. On a quiet server that means a metric wobbling by a hundredth of a percent produces a confident change point. A minimum effect size, refit against this GPU corpus rather than guessed, gates candidates before the expensive layers run.

Second substrate

The same engine, on eleven microservices

The engine began as microservice RCA over Google Online Boutique — cAdvisor telemetry, Chaos Mesh fault injection, eleven services on Kubernetes. Retargeting it at vLLM meant writing a domain adapter, not a new pipeline: the metric registry and the graph below are domain-specific, and layers 1–8 are untouched.

It is shown here as evidence that the core generalizes across two unrelated causal substrates — not as a second result. There is no labelled fault corpus for this domain and therefore no accuracy number, and an unmeasured demo is not a claim.
