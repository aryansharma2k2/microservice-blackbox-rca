When p99 TTFT spikes, which subsystem did it?

Every LLM-serving team alerts on time-to-first-token. Almost nobody can say what made it spike. There are four usual suspects: KV cache pressure, batch scheduling, prefix-cache collapse, and preemption. They look nearly identical from the outside, and each one can cause the others.

So this is an eight-layer change-point pipeline pointed at the inside of one process. It ranks mechanisms, not services. Scored on — labelled runs from a real L4 GPU, against three simple baselines and against Claude Opus 5 given the same evidence.

Measured, not asserted

Does eight layers of statistics beat the obvious thing?

A top-1 number alone tells you nothing about whether eight layers were worth writing. Every method below sees the same evidence, from the same — runs, scored the same way. Threshold alerting wins top-1. It is also useless past its first guess. That is the honest shape of the result.

How to read this

Threshold alerting fires runbook rules in order. Its first guess is decent. Its second is noise, which is why its top-3 never improves on its top-1. Correlation ties on top-1 and loses 13 points of top-3. That is exactly what it should do: it cannot separate a cause from its own effect. Topology ignores the telemetry completely and still clears 58% top-3, which is the floor any real method has to beat. It also names something on every clean run. Claude Opus 5 is genuinely competitive on the same evidence. The gap is that it never sees onset timing, and onset timing is what the pipeline ranks by.

The reframe

An inference server is one service — so localize inside it

An inference server is a single process. There are no services to rank, so a straight port of microservice RCA has nothing to work with. The fix is to rank mechanisms instead. Cache occupancy drives preemption, preemption drives queueing, queueing drives TTFT. That is a real causal graph. The statistical core needed no changes at all: only this graph and the metric list are specific to vLLM.

Exogenous. An input you do not control. Traffic always moves first, so ranking purely by what moved first would blame load for everything. These nodes can still produce a capacity verdict, but are never named as a fault.

SLI. The thing being explained. It is excluded from its own suspect list, so the engine cannot answer “TTFT is slow because TTFT is slow.”

Mechanism. A subsystem, backed by one or more Prometheus series. Hover a node to see its metrics.

The part most projects omit

Where it fails, and why

Rows are what was injected. Columns are what the pipeline named. A perfect diagnoser is a diagonal line. This one is not, and the misses have a single dominant cause.

Measurement modality outranks causality

The pipeline ranks by what moved first. But it reads “first” from the telemetry, not from the event itself. Gauges report immediately: kv_cache_usage_perc and num_requests_running show their new value on the very next scrape. Windowed rates and histogram quantiles do not. They only reach their new value once the window has filled, roughly half a window late.

So an effect read from a gauge beats its own cause read from a rate. Two mechanisms here are read from gauges: kv_cache_pressure and batch_composition. Those are exactly the two columns collecting the misses.

The pipeline shifts each series back by half its window to compensate, which is worth 2.7 points of top-1 on this corpus. It is a patch, not a fix. Fixing it properly means changing what gets measured, not how it gets ranked.

A quarter of the corpus never had a clean baseline

—

Each run records a baseline, injects a fault, then records the fault window. Sometimes the previous run's load had not finished draining. When that happens, the baseline window opens with p99 TTFT already a hundred times its own median.

That breaks the detector. Layer 1 works out a mean and a standard deviation from the baseline window. A huge standard deviation means nothing in the fault window ever looks unusual enough to flag. The validity check passes these runs because it only asks whether the load generator was keeping up. It was. The server was just still busy with the last incident.

The headline number counts all — runs anyway. Dropping a quarter of your corpus raises your score. That is a move you make in the open or not at all.

The SLI is coarsely bucketed

vllm:time_to_first_token_seconds is a histogram, and p99 is interpolated from its buckets. Across these traces the quantile spends most of its time stuck on two values, 0.248 s and 159.2 s. Those are bucket edges, not measurements. Real but small TTFT movements are invisible, and the SLI reads as a staircase instead of a curve. Getting finer detail means setting custom bucket boundaries at deploy time.

Method

Eight layers, and what each one is for

  1. 1

    CUSUM + block bootstrap

    Find candidate change points in each metric. The detection threshold is measured, not assumed: it is the 95th percentile of 1000 resamples of the baseline. Seeded per component and metric, so results are reproducible.

  2. 2

    Markov normal model

    Drop changes that a model of learned-normal behaviour still predicts. Detectable is not the same as abnormal.

  3. 3

    FFT burst filter

    Remove periodic workload bursts that are expected at this frequency, so a predictable traffic shape does not register as an incident.

  4. 4

    Tangent rollback

    A detector fires after a trend starts. Roll each crossing back along its tangent to estimate when the deviation really began. Every later layer depends on that number.

  5. 5

    Multi-metric aggregation

    Collapse per-metric onsets into one onset per mechanism, and apply lag compensation for windowed metrics.

  6. 6

    Exogenous check & verdict

    Say the first thing to move is an input you do not control, and load is climbing. The answer is capacity: you are overloaded, nothing is broken. Now say load is flat and something internal moves first. That is a pathology. One means add a replica. The other means fix your config.

  7. 7

    Propagation chain

    Order candidates by onset, treating near-simultaneous fires as concurrent rather than sequential.

  8. 8

    Dependency filter

    Demote any mechanism the graph already explains as knock-on from something earlier. This stops the engine reporting one symptom chain as five separate faults.

The effect-size gate

Layers 1–4 ask whether a change is detectable. They never ask whether it is large. On a quiet server a metric wobbling by a hundredth of a percent produces a confident change point. So a minimum effect size filters candidates before the expensive layers run. The threshold was fitted against this corpus, not guessed.

Second substrate

The same engine, on eleven microservices

The engine started as microservice RCA over Google Online Boutique: cAdvisor telemetry, Chaos Mesh fault injection, eleven services on Kubernetes. Retargeting it at vLLM meant writing a domain adapter, not a new pipeline. Only the metric list and the graph below are domain-specific. Layers 1–8 never changed.

It is here as evidence that the core works on two unrelated kinds of system. It is not a second result. There is no labelled fault corpus for this domain, so there is no accuracy number, and an unmeasured demo is not a claim.

git clone https://github.com/aryansharma2k2/microservice-blackbox-rca
cd microservice-blackbox-rca
pip install -e ".[dev]"

make eval
# re-diagnose one captured run
python -m eval.replay traces/vllm/—

python -m rca_engine.scripts.gen_portfolio_data
